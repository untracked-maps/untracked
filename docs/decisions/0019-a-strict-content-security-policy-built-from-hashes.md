# A strict Content Security Policy, built from hashes

## Context and Problem Statement

The app is a static site, prerendered by SvelteKit ([0004](0004-a-sveltekit-site-prerendered-as-static-files.md)) and hosted where no custom header can be sent. Of the usual threats to web applications, what applies to it is injection in the browser: a script or a style that the site did not write, run in its pages. The data it shows comes from outside ([0002](0002-a-static-client-app-reading-map-data-from-outside-behind-ports.md)), and some of it holds links, which a malicious or mistaken source could turn into a script. The browser may call only the services the app declares ([0018](0018-the-browser-talks-only-to-declared-services.md)).

Two small scripts must run before the first paint, so that a theme or a welcome kept on the device ([0017](0017-data-stays-on-the-device-without-a-server.md)) shows at once instead of flashing; SvelteKit's route announcer carries one fixed inline style.

How does the site make sure that only its own code runs, with inline code it cannot avoid?

## Decision Drivers

- Only code written for the site runs in its pages.
- No exception for inline code beyond the exact text that needs it.
- A change to an inline script never needs its allowance updated by hand.
- External data is shown, never run.

## Considered Options

- A policy generated by SvelteKit in hash mode, inline code allowed by its hash computed at build, no raw HTML
- Inline code allowed by `'unsafe-inline'`
- The pre-paint scripts as external files, allowed by the site's own origin
- No pre-paint script

## Decision Outcome

Chosen option: « A policy generated by SvelteKit in hash mode, inline code allowed by its hash computed at build, no raw HTML », because it allows exactly the inline code the site writes, and nothing else, on a host that sends no header.

### The policy allows the site and the declared services only

SvelteKit generates the policy in hash mode, delivered in a meta tag of every page: scripts, styles, fonts, workers and connections from the site itself, images from the site or inline data, connections to the declared services, no plugin, no base nor form target elsewhere. End-to-end tests check the policy, and the performance audit fails on any violation reported in the console.

### Inline code allowed by its hash, computed at build

The scripts that run before the first paint are written once, in configuration, put into the page by a server hook while prerendering, and allowed by their hash, which the build computes from the same text. The announcer's style is allowed the same way. Nothing parses the built HTML to find them, and changing their text changes their hash at the next build.

### No raw HTML

No component inserts raw HTML: the linter refuses it. Every text reaches the page through the framework's escaping.

### External data never becomes an executable URL

A link read from the data is written as a web link, and a scheme that can run code is neutralised in the presenter that writes it. Images named by the data are only paths of the site itself: an address of another site, a scheme or a climb out of its folder is left out.

### Consequences

- Good, because a script injected in a page does not run, and inline code is allowed text by text.
- Good, because the allowance of each inline script follows its text, with nothing to update by hand.
- Good, because a malicious value of a source cannot turn a link or an image into a script.
- Bad, because the announcer's hash changes if SvelteKit changes its style: the audit then fails until the style is updated.
- Bad, because a meta tag cannot carry every directive a header can, such as reporting or framing rules.
- Neutral, because each new service is a change of the policy, made with the feature that calls it.

### Confirmation

End-to-end tests check the policy and that pre-paint scripts run under it; the performance audit fails on a violation; the linter refuses raw HTML.

## Pros and Cons of the Options

### Inline code allowed by `'unsafe-inline'`

No hash to compute. But it allows any inline script or style, an injected one included, which voids the policy.

### The pre-paint scripts as external files, allowed by the site's own origin

No hash at all. But a blocking request more before the first paint, and a script outside the checks of the sources.

### No pre-paint script

Nothing inline to allow. But a visitor who chose a dark theme on a light device sees a light page first, and a welcome already acknowledged flashes.

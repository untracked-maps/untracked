# ADR-013 — Releases with semantic-release, published to GitHub Pages

**Date**: 2026-11-15
**Status**: accepted

## Decision

Every push to `main` runs the checks, then semantic-release:

1. It derives the version from Conventional Commits: `fix` for a patch, `feat` for a minor, a breaking change for a major.
2. It updates `package.json`, `CHANGELOG.md` and the `Current version` line of the README, commits them as `chore(release): x.y.z [skip ci]`, tags `vx.y.z` and creates the GitHub release.
3. A second job checks out the tag, builds the site, publishes it with `actions/deploy-pages`, and attaches the build as a zip to the release.

A push without a `feat` or `fix` commit releases and publishes nothing.

### Permissions

Every workflow starts from `contents: read`, and a job asks only for what it needs:

- `release` only reads with the workflow token: it writes the release commit and tag, and comments on the issues and pull requests a release closes, with a token of the `untracked-maps-release` GitHub App (contents, issues and pull requests in write, installed on this repository only), generated by `actions/create-github-app-token` from the `RELEASE_APP_CLIENT_ID` variable and the `RELEASE_APP_PRIVATE_KEY` secret, and limited to those three permissions rather than inheriting the installation's;
- `deploy` attaches the build to the release (`contents: write`), publishes to Pages (`pages: write`) and proves its identity to Pages with an OIDC token (`id-token: write`).

- `codeql` and `all-dependencies` in the security workflow upload their findings to code scanning (`security-events: write`);
- `scorecard` reads the workflows' runs (`actions: read`), uploads its findings (`security-events: write`) and publishes its score with an OIDC token (`id-token: write`).

These reasons live here rather than in the workflows, which carry no comments; zizmor's `undocumented-permissions` audit, which asks for such comments, is turned off.

## Consequences

- `main` is protected by a ruleset: no deletion, no force push, a linear history, signed commits, and the checks of the pull request green on the commit pushed. The `untracked-maps-release` App is the only actor allowed to bypass it, since GitHub lets only an App of the organisation do so, not the workflow token: the release commit, created by semantic-release in the runner, is neither signed nor checked.
- Two more rulesets govern the other branches. "Staging branches" requires a linear history on the branches named after a Conventional Commits type (`build/`, `chore/`, `ci/`, `docs/`, `feat/`, `fix/`, `perf/`, `refactor/`, `revert/`, `style/`, `test/`) and on `renovate/`, as in la Coop and ihexa; force pushes and deletion stay allowed, to rebase and clean up. It does not require signed commits: a branch rebased onto `main` carries the unsigned release commits, which such a rule refused, so that after each release no open pull request could be brought up to date. Signatures are required where commits land, on `main`. "Allowed branch names" restricts the creation of any other branch but `main`, so that a branch with another name is refused on push. Whether Renovate signs its commits is not verified yet.

## Alternatives considered

- **Tags without a release commit**: the README could not show the version.
